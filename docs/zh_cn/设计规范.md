#### 点档位的实现（重要）

婚宴档位是**竖排卡片列表**，默认选中的是列表第一个。

之前 `_click_banquet` 是 `run_task("Event_WeddingTitleButton")` 再靠 `pipeline_override` 去改子节点
`Event_WeddingTitleEntry.expected` —— 子节点不一定吃这个 override，结果等于**一直在点默认那一档**，
所以表现成「档位没生效、每次都是第一个」。

现在改成**直接跑 OCR 节点本身**：

1. 先 `Event_WeddingSweepUp` ×4 翻回列表顶部
2. `run_task("Event_WeddingTitleEntry")`，override 带 `expected=[目标档位]`、`next=[]`
3. 命中就点，日志打印命中的 OCR 文本（`已点选「乡村筵席」（OCR=乡村筵席，第 N 次尝试）`）
4. 没命中就 `Event_WeddingSweepDown` 往下翻一页再找，最多 8 页
5. 翻完没有 → 返回 False，走按爵位回退

- 档位选项在**任务启动时**就写进 pipeline，跑月度循环途中在网页上改选项不会影响正在跑的这一轮，要重启任务才生效
- 「自动（按爵位）」+ 公爵 → 乡村筵席；如果不想掉士气，把选项固定成「祝福婚宴」/「乡村筵席」并看日志确认点中

### 婚宴确认与快捷补齐

选完档位会弹「婚宴确认」弹窗，里面按材料逐行列出「需要/拥有」。**判断资源够不够，看弹窗里有没有加号**：

| 情况 | 界面表现 | 处理 |
|------|----------|------|
| 材料都够 | 没有加号，「确定」是可点的 | 直接点「确定」，婚礼开始 |
| 缺材料 | 缺的行右侧有加号，「确定」是**灰色**的（点了没反应） | 先点加号补齐，再点「确定」 |

点加号分两种：

- **只有一个加号**（只缺一种材料）→ 点它，弹出「购买」窗口（数量 + 价格 + 确定），点「确定」用银币买缺的数量
- **多个加号**（底部多出一行「快捷补齐缺少资源」）→ 点**最下面**那个加号，弹出「市场供应充足，补充目前缺少的资源消耗如下：」，点「确定」一次性补齐

补齐后回到婚宴确认（数字变成 25/25），再点「确定」，婚礼才开始，然后连点 4 下过场。

> 早期版本用 OCR「快捷补齐缺少资源」这行文案判断缺材料——只缺一种材料时这行**不出现**，会误判成“资源已齐”然后一直点灰色确定。现在改成模板匹配加号，两种布局都能识别。

节点：

| 节点 | 作用 |
|------|------|
| `Wedding_BanquetConfirm` | OCR「婚宴确认」，判断弹窗在不在 |
| `Wedding_AnyPlus` | 模板 `Marry/plus.png`，弹窗内找任意加号：命中 = 缺材料（也用于点击唯一/上面的加号） |
| `Wedding_FillPlus` | 同一模板，只在最下面那行找（多个加号时选「快捷补齐」） |
| `Wedding_BuyDialog` | OCR「购买」，识别单行加号后的购买窗口 |
| `Wedding_FillTip` | OCR「市场供应充足」，识别快捷补齐后的提示 |
| ~~`Wedding_MissingResource`~~ | 已废弃（`enabled: false`），保留只为兼容旧配置 |

代码入口：`WeddingProcessor._handle_banquet_confirm()`（`agent/action/zshg/marry.py`），在选完档位之后、点「确定」之前调用。

## 刷取任务记录（城市 / 任务 / 回合）

每次在「选择刷取任务国家」选中的城市接取任务，都会留一条记录，网页「刷取任务」页按城市分组展示，可以一键拉黑。

### 记录什么

| 字段 | 来源 |
|------|------|
| 城市 | `EnterCity` 节点的 `expected`（就是「选择刷取任务国家」的选项值） |
| 任务名 | 优先大地图左下角 HUD（`HudTaskName`：女王密令下面、剩余时间上面）；接取时也可用任务板 HUD 的名字 |
| 任务类型 / 等级 | 接取时任务板 HUD 识别结果（`HudTaskInfo`） |
| 花费回合 | 战斗会话 `BattleSessionState.confirmed_rounds` |
| 结果 | 胜利 / 失败 |

任务名的兜底顺序：

1. 接取时任务板 HUD 读到的名字（新接任务）
2. 大地图左下角 `HudTaskName`（续跑已接取任务时；HUD 那行就是当前任务名）
3. 战斗 + 战后流程结束后，如果名字还是空的，`finalize_task_record()` 会回大地图再读一次 `HudTaskName` 补上

> 所以记录要等「战后回到大地图」才落盘，而不是战斗一结束就写——这样才能补到名字。

### 什么时候写

- 接取成功：`_accept_new_task()` 点完「接受」后 `task_records.set_pending(...)`
- 已接取任务（续跑）：`_preprocess_accept_task()` 先读大地图 `HudTaskName`，读不到再用任务板「放弃」那条的名字
- 战斗结束：`_process_fighting()` 的 `_finish()` 只暂存回合数与胜负；`start_task()` 末尾 `finalize_task_record()` 补名并写盘

### 存哪

| 文件 | 内容 |
|------|------|
| `table/task_records.jsonl` | 明细，一行一条（时间/城市/任务/类型/等级/回合/结果） |
| `table/task_records.json` | 汇总：`cities → 城市 → 任务 → {count, rounds_total, rounds_avg, last_rounds, last, type, level}` |
| `table/task_blacklist.json` | 黑名单（和任务板识别器共用） |

### 一键拉黑

- 网页「刷取任务」页每行有「拉黑」按钮，写入 `table/task_blacklist.json`，下方黑名单区可「解除」
- `TaskBlacklist` 按文件 mtime 自动重载，**不用重启**，下一次扫描任务板就跳过该任务
- 接口：`GET /api/task-records`、`POST /api/task-records/blacklist`、`POST /api/task-records/unblacklist`

## 任务失败处理

刷取任务失败（战斗失败 / 打不起来）时，按「任务失败处理」选项走：

| 选项 | 行为 |
|------|------|
| 换任务（默认） | 点掉失败结算页 → 回大地图 → 放弃该任务 → 月度循环继续（下个月重新接任务） |
| 继续任务 | 保持任务接取，立即重试同一任务（最多 `TASK_FAILURE_RETRY_ATTEMPTS=2` 次）；仍失败则放弃该任务并继续月度循环，**不会因此停止年度任务** |
| 拉黑并换任务 | 先把失败任务名写进 `table/task_blacklist.json`，再放弃并继续循环 |

- 选项存进 pipeline 节点 `TaskFailSelect`（`expected` = `switch` / `retry` / `blacklist`）
- **失败结算页必须先点掉**：不点的话，月度恢复 `_recover_yearly_to_bigmap()` 会判定“战斗失败结算页”并直接停止整个年度任务——之前一次失败就整轮停掉就是这个原因
- 实现：`_handle_task_failure()`（分派）、`_retry_failed_task()`（retry 真正重打同一任务，最多 2 次）、`dismiss_battle_result()`（点结算页 + 残留确认框）、`abandon_accepted_task()`（任务板放弃当前任务）
- 回合数记录：`_finish()` 改成直接用战斗会话对象取 `confirmed_rounds`，避免战后 `session_key()` 变化导致记成 0 回合

## 事件处理与任务

**事件处理和任务是同一个概念**：pipeline 里一条 `next` 链就是一个任务，`custom_action` 是它的处理器。所以每个事件处理器都应该在任务列表里有入口——既被自动流程调用，也能停在事件页面上单独跑、单独调选项，而不是只藏在事件扫描后面。

| 事件 | 识别节点 | 处理入口 | 任务列表入口 | 月度循环会自动处理 |
|------|----------|----------|--------------|--------------------|
| 佣兵加入 | `Event_MercenaryJoin` | `handle_mercenary_join()` / `Auto_MercenaryJoinEvent` | 事件：佣兵加入 | 是 |
| 佣兵生娃 | `Event_MercenaryBaby` | `handle_mercenary_baby()` / `Auto_MercenaryBabyEvent` | 事件：佣兵生娃 | 是 |
| 孩子夭折 | `事件_孩子夭折了` | 同节点链 | 事件：孩子夭折 | 是 |
| 丰收节事件 | `Event_HarvestFestival` | `Event_HarvestFestivalDealWith` | 事件：丰收节结算 | 是 |
| 口粮预交 | `Event_HarvestFestivalPrePay` + `Event_RationPrepayEnough` | `handle_ration_prepay()` / `RationPrepayTask` | 事件：丰收节结算 | 是（粮食充足才点确定） |

| 佣兵退休 | `Event_MercenarieRetire` | 同节点链 | 事件：佣兵退休 | 是 |

规则：

- 事件处理器只写一份（函数或节点链），任务入口和自动流程都调它，任务里不复制逻辑。
- 新增事件时三步：写识别节点 → 写处理函数/节点链 → 加任务入口（`tasks/<entry>/task.json` + `taskpack.py build`）。
- 有选项的事件（佣兵加入、生娃、告白失败、婚礼、启航节）把选项挂在对应任务上；选项本身仍是 pipeline 数据节点，读写方式不变。

## 口粮预交（粮食充足才点确定）

丰收节 / 年末会出「口粮预交」面板：标题「口粮预交」，中间是「粮食消耗/年 5232」和「粮食 69449 / 5232」，够的时候显示「粮食充足」，底部「调配」「确定」。粮食不足时点确定会扣士气，并让孩子带上营养不良等负面特性，所以不能盲点。

判断顺序（`handle_ration_prepay()`，`agent/action/fight/fight_processor.py`）：

1. 面板出现「粮食充足」→ 充足；
2. 读到「拥有 / 消耗」数字对（实际面板如 `粮食 69449 / 5232`）→ `拥有 >= 消耗` 才算充足；

- 写 `temp/ration_short.json`（state、reason、need/have、时间）；
- 推送 + 弹窗提示「先补粮」；
- `post_stop()` 暂停，把面板留在原地，玩家可以直接调配 / 买粮后再继续。

节点：`Event_HarvestFestivalPrePay`（识别面板）、`Event_RationPrepayEnough`（粮食充足）、`Event_RationPrepayShort`（粮食不足）、`Event_RationPrepayAmount`（数字兜底）、`Event_RationPrepayConfirm`（确定）、`Event_RationPrepayHandle`（Custom Action：`RationPrepayTask`）。

## 未知界面与返回（UnknownGuard）

### 为什么要有

以前年度恢复（`_recover_yearly_to_bigmap()`）遇到 `_recovery_state()` 返回 `unknown` 时直接 `return False`：日志只有一句「年度流程处于未知画面，停止恢复」，既不知道卡在哪一屏，也不知道是哪个任务、哪行代码走到的，更没法下次自动处理。现在的原则：

1. 未知画面先**有界地试**，而不是立刻判死；
2. 只点**安全位置**，绝不点可能花钱 / 买东西 / 删东西的位置；
3. 画面一变就停手，重新识别，不连续盲点；
4. 真的点不动才**记录**（截图 + 调用栈 + 点过什么 + 识别探测），并且**停止当前流程**等人工；
5. 记录过的画面可以配「返回方式」，下次遇到同一画面直接照做。

### 流程

```
_recovery_state() == "unknown"
        │
        ├─ 先按画面指纹找历史记录（32×32 灰度，差 ≤ matchThreshold）
        │      └─ 有：套用 table/return_routes.json 里 unknown:<key> 的路线
        │      └─ 无：套用 default 路线
        │
        ├─ 逐步点：每点一步等 clickGapSeconds 再截图，和点之前比
        │      └─ 差 > changeThreshold → changed：停手，回到恢复循环重新识别
        │
        └─ 三步都没变化
               ├─ 有旧记录 → stuck：累加命中次数，停止
               └─ 无旧记录 → 记录到 debug/unknown/，停止
```

默认路线的三个位置（`table/return_routes.json`）：

| 步骤 | 动作 | 说明 |
|---|---|---|
| `click_bottom` | 点 `360,1010` | 「确定 / 继续」最常见的位置 |
| `back_key` | `post_click_key(4)` | 安卓返回键，弹窗 / 子页面基本都能退 |
| `click_center` | 点 `360,640` | 部分页面按钮在中间 |

判定「画面有没有变化」用 32×32 灰度指纹的平均绝对差：静态弹窗约 0；时钟、人物走动通常低于 2.0；阈值在 `settings.changeThreshold`。小动画不会误判成「变了」，真正的翻页 / 关窗会明显超过阈值。

### 数据

`table/return_routes.json`：

| 键 | 内容 |
|---|---|
| `settings` | `enabled` / `maxClicks` / `clickGapSeconds` / `changeThreshold` / `matchThreshold` / `recordLimit` / `probeOnRecord` |
| `probeNodes` | 记录时顺便跑一遍识别探测的节点（判断是不是「其实认得、只是状态机没走到」） |
| `primitives` | 动作原语：`click` / `key` / `task` / `wait`；步骤也可以直接写 `task:<节点名>` |
| `default` | 认不出的画面先怎么点 |
| `routes` | 场景 / 记录怎么回大地图；`id=unknown:<key>` 是网页为某条记录保存的路线 |

记录在 `debug/unknown/`（`debug/` 已被 `.gitignore` 忽略）：

```
debug/unknown/
  index.json                 记录列表（不含长指纹）
  snapshots/<id>/            screen.png + meta.json
  REPORT.md                  自动生成的复盘报告（给人和 Harness）
  .lock                      进程间写锁（agent 与 webapp 共用）
```

记录字段：`task` / `entry`（当时跑的任务，来自 `temp/current_task.json`）、`reason`、`attempts`（每步点了什么、有没有变化、差值）、`trace`（调用栈，第一个非本模块帧就是出现未知画面的代码行）、`probes`（识别探测命中 / 分数）、`hits`（同一画面遇到几次）、`route_*`（选的返回方式）。

### 接入点

| 位置 | 行为 |
|---|---|
| `agent/action/fight/fight_processor.py::_recover_yearly_to_bigmap` | 未知画面 → `scene_return.handle_unknown()`；changed 继续恢复，recorded / stuck 停止并记录；一次恢复最多处理 2 轮未知画面 |
| `agent/action/fight/fight_processor.py::SceneGuardTask` | 没有短事件时再看是不是未知画面；恢复算成功（组合可重试这一步），记录则返回失败（组合按失败规则停） |
| `agent/action/fight/fight_utils.py::ensure_at_bigmap` | 连续试了 ≥4 次还回不去大地图时，把最后一帧记成未知画面（只试 1~2 次的调用方不记，避免误报） |
| `webapp/runtime.py::run_task` | 启动任务写 `temp/current_task.json`（任务名 / entry），结束删除；Agent 记录时据此标注任务 |

### 网页与命令行

- `GET /api/unknowns`：列表 + 统计 + 默认路线 + 可选返回方式；
- `GET /api/unknowns/detail?id=`、`GET /api/unknowns/image?id=`：单条详情 / 截图；
- `POST /api/unknowns/route`：`{id, route}`，`route=""` 改回默认；
- `POST /api/unknowns/note`、`/delete`、`/clear`：备注 / 删除 / 清空；
- `tools/unknowns.py`：`list` / `show` / `route` / `note` / `delete` / `clear` / `report`；
- 离线自检：`python tools/selftest_scene_return.py`（37 项：指纹、记录、去重、路线、路线接回、源码定位）。

### 源码定位

`webapp/source.py` 用 AST 扫 `agent/`、`webapp/`、`tools/` 的 Python 文件，把 handler 名 / 类名 / 模块名解析成 `文件:行`，并用正则扫 `resource/base/pipeline/*.json` 的 key 找节点定义；缓存按文件 mtime 失效。`GET /api/source?symbol=` / `?node=` / `?path=&line=` 返回代码片段和 `vscode://file/...:行` 链接；`POST /api/source/open` 打开编辑器（VS Code / Cursor 命令行 → 协议 → 资源管理器兜底），路径必须落在项目目录内。


## 相亲筛选（双方种族 / 满血 / 年龄 / 月份）

### 爵位筛选：勾选状态先读再点（`ensure_filter_and_sort`）

筛选面板里的爵位是**复选框开关**——已经勾着再点一次会**取消勾选**，
结果骑士/平民全都进了候选（之前婚礼流程里混进骑士就是这个原因）。

现在的做法：

1. 点「筛选」打开面板
2. 用模板匹配读目标爵位的复选框状态：`Marry/check_on.png`（已勾）/ `Marry/check_off.png`（未勾）
   - 已勾选 → **不点**，直接确定
   - 未勾选 → 点一次，再读一次确认；还是没勾上就再点一次
   - 状态读不出来 → **先点两次「全部」清空**（先全选再取消，所有爵位变未选中），再点目标爵位
3. 点「确定」，再用 `MarryUIText` 读数量；若是 `0/...` 且选的是具体爵位，重开面板「全部」×2 清空后重新勾选

- 复选框 ROI 在 `marry_test.CHECKBOX_ROI`（全部/公爵/伯爵/男爵/骑士/平民），点击点取 ROI 中心
- 排序方向仍由 `ensure_filter_and_sort(context, 爵位, older|younger)` 控制
- 兜底：即使筛选被人为改掉，`_race_matches()` / 满血 / 年龄过滤仍会在详情页把不符的候选跳过，
  姓名里的爵位后缀也会再拦一次（见下）

### 候选无法相亲：5 秒无响应就换下一位

有些候选点「就这个」不会出现「确认向XXX发送」：已经在相亲（等回信）、被标记星星、
或特性限制不能结婚。

- `_open_send_dialog()`：**只点一次**「就这个」，然后在 `SEND_TIMEOUT = 5` 秒内轮询确认框；
  超时就判定该候选无法相亲（不再反复点按钮）
- 超时后 `_handle_blocked_candidate()`：OCR 读提示文字（有就写日志）、关掉弹窗
- 然后 `_next_candidate()`：先点「下一位」；没有这个按钮就按网格点下一个候选格
  （`_click_next_card()`，跳过已标星/正在相亲的格子），实现「直接看下一位」
- 日志：`第 N 位点击后 5 秒无响应（提示文字），直接看下一位`

### 系统命名里的爵位（快速判断）

游戏给 NPC 的系统命名是「名字 + 性别+爵位」，例如 `金枝女骑士`、`艾琳女公爵`：

- `_rank_from_name()`：从名字里认出 平民/骑士/男爵/伯爵/公爵
- 筛选选了具体爵位时，名字里的爵位对不上 → 直接取消并「下一位」（筛选项被改掉时的第二道保险）
- `_strip_rank()` / `_name_in_table()`：把 `女骑士`/`公爵` 这类后缀去掉后再和种族姓名表比对，
  这样「金枝女骑士」也能命中姓名表里的「金枝」
- `CastleMarryJustThisReadName` 的 OCR 正则放宽到 `确认向[一-龥]{1,10}发送`，带爵位后缀的长名字也能读全

### 我方种族：相亲种族

| 取值 | 多角色模式 | 单角色模式 |
|------|-----------|-----------|
| 不限（默认） | 不过滤，按每个候选人自己的血统决定国家（旧行为） | 回退到高阶精灵（单角色必须指定种族） |
| 具体种族 | 我方公爵候选的最高血统种族 ≠ 所选种族就跳过，不进入后续联姻 | 用它决定 `CastleMarrySelectCountry` 去哪个国家 |

- 节点：`MarryRaceSelect`（`expected` = 种族名 / `不限`）
- 判断在 `_race_matches()`，用在 `_process_single_candidate()` 读完血统之后
- 血统名先经 `_get_marriage_info()` 归一（含字形模糊匹配，如「宏朝贵胃」→「宏朝贵胄」），再和选项比较

### 对方种族：对方种族

| 取值 | 行为 |
|------|------|
| 跟随我方（默认） | 对方必须和我方公爵同族：国家 = 我方种族对应国家，姓名表 = 我方种族姓名表 |
| 指定种族 | 去该种族对应国家找对象，姓名相亲要求对方姓名落在**该种族姓名表**里 |

- 节点：`MarryTargetRaceSelect`（`expected` = `same` / 种族名）
- 实现：`_evaluate_bloodline_and_get_target()` 返回 `(我方种族, 对方种族, 对方国家)`，
  对方种族还会写进 `_current_race` 供聊天模式的面部特征模型选择
- 例：我方=公爵·高阶精灵、对方=高阶精灵 → 去森之祈愿、按高阶精灵姓名表匹配

### 是否满血

- 「是」时要求我方公爵最高血统 = **100%**（如「高阶精灵 100%」），低于 99.5% 直接跳过该候选
- 节点：`MarryFullBloodSelect`（`expected` = `yes` / `no`），实现 `_get_full_blood_only()`
- 血统百分比来自 `RolePanel_BloodPage` 识别结果（`Bloodline.bloodlines`）

### 年龄：相亲年龄区间

任务页填两个数字（**0 或留空 = 该侧不限**），三种用法：

| 想要的区间 | 最小年龄 | 最大年龄 |
|-----------|---------|---------|
| 小于 60 岁 | 0 | 60 |
| 60 ~ 120 岁 | 60 | 120 |
| 大于 120 岁 | 120 | 0 |
| 不限 | 0 | 0 |

- 节点：`MarryAgeMin` / `MarryAgeMax`（由 input 选项的 `{最小年龄}` / `{最大年龄}` 占位符写入）
- 列表扫描阶段就按区间跳过（`_find_available_candidates`），详情页再兜底判一次（`_check_and_filter_by_age`）
- 下限 > 上限时自动交换并打 warning
- 实现：`_get_selected_age_range()` / `_age_matches()`

#### 年龄排序

任务页「年龄排序」：自动（默认）/ 从大到小 / 从小到大。

- 自动：**只设了上限**（例如 `0 ~ 35 岁`）时按**从小到大**排，其余按从大到小
  （否则 0~35 这种区间会被一堆 200 岁的老家伙挡在列表顶部，扫不到年轻人）
- 节点 `MarryAgeOrderSelect`（`auto` / `desc` / `asc`），实现 `_age_sort_pref()`
- 排序方向交给 `ensure_filter_and_sort(context, 爵位, older|younger)`

### 逐娃相亲（一个娃只发一封）

`_single_plan` / `_main_process` 都是**按娃循环**：

1. 扫列表拿到可相亲的娃（`_find_available_candidates`）
2. 对每个娃：**长按卡片 3 秒**（不行再 5 秒，`_enter_role_details`）打开角色详情 → 读血统 → **判断这个娃的种族** → 去对应国家
3. 在对方国家列表里点「就这个」→ 读「确认向XXX发送」→ 姓名命中该种族姓名表就发信
4. **一个娃只发一封**，然后回到联姻主界面（`_back_to_marry_main`），处理下一个娃
5. 直到回信满（8/8）或没有候选

- 单角色 / 多角色两种模式现在都会读**每个娃**的血统，不再用选项里的种族硬套国家
  （例：森之祈愿 同时是高阶精灵和法拉希尔血裔的国家，必须按娃的种族选姓名表）

### 联姻前必须轻点角色（`_tap_current_card`）

长按看完属性 → 返回列表后，游戏的「选中角色」仍停在上一次的位置（通常就是列表第一个）。
这时直接点「联姻」，联姻的对象是**默认第一个娃**，不是刚查完血统的那个——等于种族/国家判断白做。

所以 `_execute_marriage_matching()` 的顺序固定为：

```
_leave_detail()            # 从角色属性页退回列表
_tap_current_card()        # 轻点这张卡，选中刚查过属性的娃
_select_country(country)   # 点联姻 → 选国家
```

- 卡片位置来自 `_process_single_candidate` 记录的 `_current_box`
- 轻点是**短按**（长按会重新打开属性页）

### 从角色属性页退回列表（`_leave_detail` / `_back_to_marry_main`）

角色属性面板是**从底部盖上来**的，盖住之后顶部「剩余相亲对象数量：xx」**仍然可见**，
所以不能用“能识别到数量文字”判断已经回到列表——否则会认为早就回列表了，一次返回都不按，
表现就是**反复查看同一个角色属性、不返回**。

- `_enter_role_details()` 成功时置 `_in_detail = True`
- `_leave_detail()`：有状态位时按一次 `BackButton_500ms` 并清位；气泡挡住时再补一次
- 所有提前返回（年龄不符 / 血统不符 / 纯血不符 / 国家未知）都走 `_back_to_marry_main()` → `_leave_detail()`
- `_back_to_marry_main()` 判定“已在列表”要求：能识别数量 **且** 没有气泡
- 新增节点 `CastleMarryBusyTip`（OCR 求婚信 / 伙计 / 刚刚发出去 / 正在相亲）：
  「我的求婚信才刚刚发出去，伙计。」这类气泡会挡住返回，先点掉
- 队列索引规则：**嫁出一个娃后 index 不动**（卡片移出、后面整体前移），只有“跳过”才 +1

### 姓名匹配循环（`_match_name_in_loop`）

点「就这个」→ 读「确认向XXX发送」→ 命中姓名表就发信，否则「下一位」。

- 发信成功即返回（一个娃一封），由外层循环换下一个娃
- 读不到弹窗 / 读不到姓名时不直接退出：取消 + 「下一位」继续
- 一个娃最多试 `_current_max_attempts` 次（单角色 = 相亲对象总数）
- 结束时汇总用 `_name_attempts`（实际尝试次数）和实际发信数

聊天模式（`_execute_chat_matching`）同样一个娃一封，`_accept_candidate()` 统一发信。

### 选国家：有界翻页（`_select_country`）

之前 `CastleMarrySelectStart` 用 pipeline 里的 `[JumpBack]` 翻页链，国家不在当前页时会一直翻，
卡满 25 秒看门狗后整轮被迫停止（2026-10-28 13:15 就是这么停的）。

现在改成脚本自己控制：

1. 点「联姻」（override `next: []`，不让 pipeline 继续跑链）
2. 最多翻 8 页：每页先查「被拒绝啦」，再看目标国家是否出现
3. 找到 → 点国家 → 确定；翻完没有 → 返回 False，只跳过这个娃，不再卡死

发完/失败后用 `_back_to_marry_main()` 确认回到联姻主界面（能识别「剩余相亲对象数量」），
回不去才设置 `_stop_requested` 结束整轮。

### 月份：城堡相亲月份

- 任务页「城堡相亲月份」（1~12 月，默认 4 月）→ 节点 `MarryMonthSelect`
- `handle_festival_by_month()` 到这个月就调 `handle_marry_festival(context, month=该月)`；
  「4月城堡相亲」选项仍控制 自动 / 跳过 / 手动
- 5 月若把月份也设成 5，会优先按城堡相亲处理（春林节让位）
- 推年计划的组合步骤里可以单独覆盖这些选项（每个步骤有自己的 selection）





## 战斗记忆与策略

战斗记录、攻击权重、自动学习与按回合选任务的完整说明见
[战斗记忆与策略.md](战斗记忆与策略.md)。要点：

- 每场战斗写 `table/battle_memory.json`：开局/每回合敌我位置、攻击/移动决策、回合、胜负、策略；
- 首次战斗测量地图尺寸（行 × 列，如 13 × 15）并记录初始位置；网页「编辑位置」可
  用图形格子/JSON 修正，修正后 `source=user`，自动测量不再覆盖；
- `table/battle_policies.json` 用权重描述目标选择（distance / hp_ratio / threat）与移动模式
  （approach / defensive / hold / explore），网页「战斗记忆」可编辑；
- 统计会自动推荐并启用打得最快的策略，每 5 场换一个采样最少的策略做探索；
- 接任务选项「任务选择策略=回合最少/均衡」按预计回合排序，未知任务先乐观采样一次；
- 回合数：会话 key 改为进程级固定值（避免嵌套回调各拿一个会话）；记录
  「实际发生行动的最后一回合」，结算时到达的回合号另存 `rounds_reached`
  （20 回合结束、第 21 回合结算仍记 20 回合）。
