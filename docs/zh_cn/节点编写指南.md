## 1. 状态机结构总览

MaaFramework Pipeline **不是纯 FSM**，有两种边：

| 边类型 | 语法 | 语义 |
|--------|------|------|
| 状态转移 | `"next": ["X"]` | 命中 X 后，X 接管控制(常规推进) |
| 异常处理 | `"next": ["[JumpBack]X"]` | 执行 X, **自动返回当前节点的 `next` 继续找**。用于计划外情况: 弹窗拦截、列表滑不到目标、异常分支回退。**不是普通子例程**——用得越少越说明状态机干净 |

把整张图打开 `pipeline_overview.html`，13 个文件作为复合状态分组。可以观察到的几个核心模式：

### 入口层（用户级 / Python 级）
- `interface.json` 暴露 5 个用户入口：`📲 启动游戏` / `📲 每日礼包和密令` / `📲 推年计划` / `📲 自动孩子取名字` / `📲 自动相亲`
- `agent/**.py` 调 `context.run_task()` 33 处（详见 `pipeline_external_entries.html`）

### 状态机层（orchestrator）
**纯调度节点**，无 `recognition` / `action`，只有 `next`：
- `GameStartUp` (start_up.json) — 启动游戏，串 `AppStartUp` / `GameClickInform` / `GameLoading` / `GameEnterGame`
- `CastleHall` (marry.json) — 联姻大厅入口，串 `CastleMarryWindow` / `[JumpBack]CastleMarryEntry` / `[JumpBack]CastleHallEntry` / `[JumpBack]CastleEntry` / `[JumpBack]CastleSwipeDown`
- `BigMapRewardToken` (main_ui.json) — 大地图领取王族/女王密令
- `GrowthTrial_Start` (growth_trial.json) — 跨页面活动流程入口
- `FightResult_ReturnBigMap` (city.json) — 战斗结果 → 领奖 → 回大地图
- `Event_HarvestFestivalDealWith` (event_utils.json) — 丰收节 4 个分支用 `[JumpBack]` 串接

**口诀**：orchestrator = "我可能在 A/B/C/D 状态，挨个试，命中谁走谁"。

### 叶子层（action / wait / utility）
详见下一节。

## 2. 5 种节点角色

| 角色 | 特征 | 例子 |
|------|------|------|
| **A. Orchestrator（调度）** | 仅 `next` 列表 | `CastleHall`, `GameStartUp`, `OpenCityTaskPanel` |
| **B. Process（动作+转移）** | `recognition` + `action` + `next` | `CastleMarryEntry`, `Temple_Ancestor_Entry`, `BigMapMarketShopBuy1` |
| **C. Wait / Hold（页面确认）** | `recognition` + `expected`，**无 action 无 next** | `InTaskPannel`, `UI_MainWindows`, `CastleMarryWindow`, `Event_WeddingPage` |
| **D. Utility（复用工具）** | `recognition` + `action`，**无 next**，只通过 `[JumpBack]` 调 | `BackButton_500ms`, `ClickCenter_500ms`, `PopUpWindowConfirm` |
| **E. External Entry（用户/Python 入口）** | `DirectHit` + `Custom` action，或 `enabled: true` 的 Flag | `Auto_FightTask`, `Auto_DailyTask`, `Flag_EnableMarryTask` |

**常见错误**：
- 把 D（utility）写成"有 next 链" → 它被串接后会脱离"返回调用方"的语义
- 把 C（wait）写成"有 action" → 不需要点击就什么都别点
- 把 B（process）`next` 写成空 → 应该用 C（wait）替代

## 3. 节点模板（按角色）

### 3.1 Orchestrator（A 角色）

```jsonc
{
    "MyTask_Start": {
        "next": [
            "MyTask_AlreadyOnTarget",         // 已经在目标页
            "[JumpBack]MyTask_NavigateFromA",  // 可能从 A 页面来
            "[JumpBack]MyTask_NavigateFromB"   // 可能从 B 页面来
        ],
        "timeout": 10000
    }
}
```

**关键点**：
- 不写 `recognition`（不识别任何东西）
- `next` 第一个通常是 **同文件内的 C 类 wait 节点**（证明状态正确就停）
- 其它项是 `[JumpBack]`（执行完自动返回，重新从 `[*]` 开始找）
- `timeout` 一定要设，否则 task 启动时如果没匹配任何子节点会无限等

**最佳实践**：`MyTask_Start` 通常也是 task 的 entry（即 `interface.json` 中 `task[].entry` 指向的节点）。

### 3.2 Process（B 角色）

```jsonc
{
    "CastleMarryEntry": {
        "attach": {
            "description": "城堡联姻（点击联姻按钮）"
        },
        "recognition": "OCR",
        "expected": [
            "联姻"
        ],
        "roi": [107, 246, 526, 774],
        "order_by": "Vertical",
        "action": "Click",
        "post_delay": 1000,
        "timeout": 2000
    }
}
```

**关键点**：
- **必须**有 `attach.description`（自文档化，代码 review 时一眼看懂）
- `expected` 写**屏幕实际显示的完整文本**（中文 / 英文 / 拼音都行，关键是**和屏幕一致**）
- 字符级别的容错用 `replace`（如 `事件_孩子夭折了` 的 `[["天","夭"]]`）
- 终止节点**统一写 `"next": []`**（不要省略字段）
- 滚动列表中的项可以**在 `next` 末尾**挂 `[JumpBack]SwipeXxx` 作为兜底（见 §8.2）
- 不需要 `attach` 的是 `expected` 已自解释 + `roi` 收得很窄的简单节点

### 3.3 Wait / Hold（C 角色）

```jsonc
{
    "InTaskPannel": {
        "recognition": "OCR",
        "roi": [284, 6, 149, 108],
        "expected": "任务",
        "timeout": 2000
    }
}
```

**关键点**：
- 命中即停（task chain 完成）
- 用作 orchestrator 的"首项"——证明状态正确就退出
- ROI 要窄，避免误识别

### 3.4 Utility（D 角色）

```jsonc
{
    "ClickCenter_500ms": {
        "recognition": "DirectHit",
        "action": "Click",
        "target": [360, 640, 10, 10],
        "post_delay": 500,
        "timeout": 2000
    },
    "BackButton_500ms": {
        "recognition": "TemplateMatch",
        "template": "return.png",
        "roi": [603, 0, 117, 140],
        "post_delay": 500,
        "timeout": 2000,
        "action": "Click"
    }
}
```

**关键点**：
- **绝对不要**写 `next`！Utility 是纯副作用
- 调用方必须用 `[JumpBack]ClickCenter_500ms` 调用
- 目前 `main_ui.json` 有 11 个工具节点，**新 utility 必须加到 main_ui.json**，不要散落

### 3.5 External Entry（E 角色）

```jsonc
{
    "Auto_FightTask": {
        "recognition": "DirectHit",
        "action": "Custom",
        "custom_action": "TaskProcessor",   // Python 端 MaaFramework CustomAction
        "post_delay": 500,
        "timeout": 2000
    },
    "Flag_EnableMarryTask": {
        "enabled": true                     // 开关，由 Python 侧读 node_data 用
    }
}
```

**关键点**：
- E 角色是 `interface.json` 的入口
- 必须有 `recognition: "DirectHit"`（pipeline 协议要求）即使没真实识别
- Python 端通过 `context.run_task("Auto_FightTask")` 触发
- `Flag_*` 节点用于运行时开关（`context.get_node_data("Flag_EnableMarryTask")`）

## 4. 可复用工具节点（`main_ui.json`）

`main_ui.json` 第 254-693 行有 11 个工具节点，**新加 utility 必须放这里**：

| 节点 | 用途 |
|------|------|
| `BackButton_500ms` | 左上角返回 |
| `BackButton_DirectHit` | 返回（用 DirectHit 避开 return.png 路径问题） |
| `ClickCenter_500ms` | 点击屏幕中心 10×10 区域（用于消弹窗 / 推进引导） |

## 5. 节点命名前缀规范

### 5.1 文件级前缀
每个节点用**所属模块**作前缀，避免和其它模块冲突：

| 前缀 | 含义 | 例子 |
|------|------|------|
| `Castle*` | 城堡相关 | `CastleEntry`, `CastleHall`, `CastleMarryEntry` |
| `BigMap*` | 大地图相关 | `BigMapMall`, `BigMapRewardToken`, `BigMap_Activity` |
| `Fight*` | 战斗相关 | `FightStart`, `FightResult_ReturnBigMap` |
| `Event_*` | 一次性事件 | `Event_MercenaryJoin`, `Event_HarvestFestival` |
| `Temple_*` | 神殿 | `Temple_Entry`, `Temple_Statue_Entry` |
| `TaskDetail*` | 任务详情 | `TaskDetailOpen`, `TaskDetailClose` |
| `FindCity*` | 城内找建筑 | `FindCityTavern_OCR`, `FindCityTask_OCR` |
| `GrowthTrial_*` | 成长试炼（活动） | `GrowthTrial_Start`, `GrowthTrial_Difficulty_Select` |
| `UI_*` | 通用 UI 元素 | `UI_MainWindows`, `UI_MapSwitch` |
| `Pannel*` / `Panel*` | 孩子面板（**注意：项目里有两种拼法都存在**） | `PannelChildInfoButton`, `PanelPropertyCheck` |
| `Flag_*` | 运行时开关 | `Flag_EnableMarryTask` |
| `Auto_*` | 用户级 task 入口 | `Auto_DailyTask`, `Auto_MarryTask` |
| `检测_` / `事件_` | 一次性中文节点 | `事件_孩子夭折了`, `检测_科内塔之怒` |

### 5.2 命名风格
- 统一 **PascalCase**（驼峰）
- **避免** 下划线分隔的 `BigMap_Activity_Resident`（与 `BigMapMall` 不一致），但**项目已有**此模式，新加时**跟着文件惯例**走
- 用名/动名要一致：要么全是动名（`Click...`），要么全是名（`MarryEntry`）—— 文件内统一即可
- **避免** 拼写错误：
  - `Reuslt` → `Result`（`FightReusltLevelUp` / `FightReusltSkillUp` 是历史遗留，新写不要学）
  - `Shuwdown` → `Shutdown`（`AppShuwdown` 同上）
  - `Pannel` vs `Panel`（项目混用，**新写统一用 `Panel`**）

### 5.3 检测/事件节点用中文
`事件_孩子夭折了` / `检测_科内塔之怒` 这种**纯中文节点名**是允许的，但建议**用 `// @i18n-skip` 注释**避免国际化误处理（参考 [pipeline-guide](../zh_cn/...)）。

## 6. 识别算法选型

| 场景 | 算法 | 理由 |
|------|------|------|
| 中文字符串 | **`OCR`** | 首选，UI 元素以文字为主 |
| 固定图标 | `TemplateMatch` | 比 OCR 稳定，比 ColorMatch 快 |
| 颜色判别（红点 / 黄点） | `ColorMatch` (HSV) | 颜色不变时最稳 |
| 表达式判断 | `Custom` (`ExpressionRecognition`) | `node_data` 派生属性 |
| 不需要识别直接点击 | `DirectHit` | **慎用**，易点错；只在"打开 app" / "中央点击消弹窗" 等固定位置时用 |

**当前使用情况**（基于 245 节点）：

- OCR ~70% 节点
- TemplateMatch ~15%
- DirectHit ~10%
- Custom / ColorMatch 极少

## 7. ROI 选取经验

### 7.1 三层粒度
1. **紧 ROI**（±10px）：`expected` 文字独立、不会与其它元素重叠时（`UI_CastlePage`：`[477, 1249, 52, 30]`）
2. **中等 ROI**（±30px）：文字可能被同屏装饰元素干扰时
3. **统一大 ROI**（覆盖整个可滚动区域）：多个同类目标在同一列表中（10 个城堡建筑都 `[100, 400, 520, 880]`）

### 7.2 经验数据（来自 `pipeline-generate` 实践）

| 节点 | 最佳 expand | 备注 |
|------|------------|------|
| `UI_RoleListPage` | 20 | 通用值 |
| `UI_CastlePage` | **3**（仅 0-15） | 上方有图标干扰 |
| 10 个城堡建筑 | **0**（统一大 ROI） | 滚动列表共用 ROI |

### 7.3 ROI 上边界容易踩坑
目标元素 y=424，ROI 起点 y 必须 ≤ 424。如果原 ROI `[100, 450, ...]` 把"城堡管理"切掉 26px，OCR 永远找不到。**`expected` ROI 起点 y ≤ 元素实际 y**。

### 7.4 720p 基准
所有坐标基于 **720×1280**。编辑 ROI 之前先确认截图分辨率（详见 [pipeline-guide](.../zh_cn/.../pipeline-guide)）。

## 8. 流程控制：`next` vs `[JumpBack]`

### 8.1 决策树
```
要接节点 X 到 Y 的"next"
│
├─ 命中 X 后让 X 接管？
│   └─ ✅ "next": ["X"]                # 真·状态转移
│
└─ 命中 X 后还要继续在 Y 上找？
    └─ ✅ "next": ["[JumpBack]X"]       # 子例程调用
```

### 8.2 滚动场景（用 `[JumpBack]` 兜底,但要谨慎）

滚动列表节点**可以**挂 `[JumpBack]SwipeXxx`,但要**保证有限次滑动内能命中**。原则:

1. Swipe 类节点必须放 `next` 列表**末尾**(优先级低)
2. 必须能保证滑 N 次后能找到——`expected` 在滑动范围内会逐次出现
3. 配 `max_hit: 1` 防止某 swipe 在一次 task 中被反复触发

**反例**(Swipe 放首位 → 死循环):
```jsonc
{
    "CastleManage": {                    // 单个建筑节点
        "recognition": "OCR",
        "expected": ["城堡管理"],
        "roi": [...],
        "action": "Click",
        "next": [
            "[JumpBack]CastleSwipeDown"  // ❌ 唯一项 → 找不到就无限滑
        ]
    }
}
```

**正例**(Swipe 末尾 + 优先走命中路径):
```jsonc
{
    "CastleHall": {
        "next": [
            "CastleMarryWindow",          // ✅ 命中即停(走真转移)
            "[JumpBack]CastleMarryEntry", // 真转移(联姻区)
            "[JumpBack]CastleHallEntry",  // 真转移(城堡主厅)
            "[JumpBack]CastleSwipeDown",  // ✅ 末尾兜底,滑一次再找
            "[JumpBack]CastleSwipeUp"
        ]
    },
    "CastleMarryEntry": {
        "recognition": "OCR",
        "expected": ["联姻"],
        "roi": [107, 246, 526, 774],
        "action": "Click",
        "next": []                        // 终止节点显式写 []
    }
}
```

**关键设计**:

- 前面几条是"已知页面状态"匹配,命中就走人
- 末尾的 `[JumpBack]SwipeXxx` 是**异常处理**:前面都没命中时才滑动一次
- 配合 `max_hit: 1` 确保一次 task 里 swipe 至多触发一次

### 8.3 `max_hit`（限次）
用于"只命中一次"的子任务（避免重复弹窗或重入子流程）：
```jsonc
{
    "BigMapRewardToken1": {
        "max_hit": 1,                    // 只命中 1 次
        "recognition": "OCR",
        "expected": ["女王"],
        ...
    }
}
```

`max_hit` 配合 `[JumpBack]` 一起用，避免 orchestrator 重复触发。

### 8.4 跨文件引用
- MaaFramework 全局加载时**所有 `*.json` 合并到同一命名空间**，`[JumpBack]OtherFileNode` 能解析
- `run_pipeline` 测试工具**只加载单文件**，跨文件引用集成测试需用 MaaPiCli GUI/CLI

### 8.5 跨页面状态机 vs Python orchestration
**反例**（用 Python for/while 模拟）：
```python
while not context.run_task("A"):
    context.run_task("B")  # ❌ 状态机该自己跳
```

**正例**（用 `[JumpBack]` 串）：
```jsonc
{
    "A": {
        "next": [
            "A_Done",
            "[JumpBack]B"               // 一次性副作用
        ]
    }
}
```

详见 [pipeline-guide §典型模式 §跨页面活动流程](.../zh_cn/.../pipeline-guide)。

## 9. 已验证的反模式

下面是项目里**已经踩过的坑**，新写节点时直接避开：

### 9.1 ❌ 硬延迟代替识别
```jsonc
"FightStart": {
    "pre_delay": 500,                   // ❌ 用 pre_delay 等动画
    "recognition": "OCR",
    ...
}
```
**正例**：用 `pre_wait_freezes: {"time": 200, "target": [0, 0, 0, 0]}` 等画面静止。

### 9.2 ❌ `expected: [""]` 写空字符串

```jsonc
"CustomTaskBlacklist": {
    "recognition": "OCR",
    "expected": [""]                    // ❌ 永远匹配空串 = 永不会命中
}
```

**正例**:

- `expected` 写**屏幕实际显示的文本**——中文 / 英文 / 拼音都行,关键是**和屏幕一致**
  - 屏幕显示"城堡" → `expected: ["城堡"]`
  - 屏幕显示 "Castle" → `expected: ["Castle"]`
  - 屏幕显示 "koneita" → `expected: ["koneita"]` (这并不是错的,只要屏幕真有这个文本)
- 字符容错用 `replace`: `"replace": [["天", "夭"]]` 把 OCR 误识的"天折"修成"夭折"
- 真正废弃的节点直接删,不要用 `expected: [""]` 占位

### 9.3 孤儿节点 = 预留节点(保留,不要删)

当前图谱中"看似孤儿"的节点:

- `BigMap_Activity_TimeLimit`, `BigMap_Activity_GiftPackage` — **预留**,未来要支持的 tab
- `YearlyTaskMonths`, `CustomTaskBlacklist` — `expected` 待补,**先不删**
- `Event_LaunchPage` 和 `Event_LaunchEnter` — 名称相近,后续整合时改名

**规则**:

1. **预留节点不要删**——`attach.description` 注明"预留: XX 流程会调"
2. **不要写 `expected: [""]`** 让节点占位——要么写真实 `expected`,要么不加 `recognition` 字段(用 `DirectHit` 占位)
3. 真正废弃的节点**才删**(确认 Python 端无引用)

### 9.4 ❌ 全角字符命名
```jsonc
"事件_孩子夭折了": {...}              // ❌ 中文节点名（虽然图谱能跑，但 hash 后名字不直观）
```
**正例**：用 `Event_ChildDeath` 风格，**事件/孩子夭折了放到 `attach.description` 里**。

### 9.5 终止节点统一显式写 `"next": []`

**项目惯例**:终止节点**显式写 `"next": []`**,不要省略 `next` 字段。

```jsonc
"CastleMarrySelectCountryConfirm": {
    ...
    "next": []                          // ✅ 明确表达"无后继"
}
"CastleMarryGetInfoButton": {
    ...
    "next": []                          // 同上
}
```

虽然省略 `next` 字段(依赖协议默认值)和 `next: []` 在协议里等价,但项目里**统一显式**更易读、review 时一眼能看出"这是终止节点"。

### 9.6 `target: [区域]` 用于"检测点变 + 点击点固定"

```jsonc
"Event_HarvestFestival": {
    "recognition": "OCR",
    "expected": "丰收节",
    "roi": [133, 234, 402, 166],
    "action": "Click",
    "target": [244, 813, 287, 261]     // ✅ 固定区域,OCR 命中位置每次可能不同
}
```

**用法场景**:

- 识别 ROI 内的目标**每次位置不固定**(不同分辨率 / 不同任务阶段)
- 但要点击的坐标**是固定的**(如"丰收节"图标旁的"前往"按钮)
- 此时 `target: [x, y, w, h]` 比 `target: true + target_offset` 更直接、更稳

**什么时候用 `target: true + target_offset`**:

- 识别和点击是**同一元素**,只是点击位置略偏(如按钮中心偏右)
- 用 `target_offset: [dx, dy, 0, 0]` 微调

### 9.7 `enabled: false` 不是死代码,是运行时开关

`Flag_EnableMarryTask` / `MarryModeSelect` / `MarryRaceSelect` / `MarryMultiSelect` 等节点 `enabled: false` 是**有意为之**——它们是 `interface.json` 给用户的**运行时开关**:

```jsonc
"Flag_EnableMarryTask": { "enabled": true }   // Python 端 context.get_node_data() 读取
"MarryRaceSelect": {
    "recognition": "OCR",
    "expected": ["佩尔弗因王族"],
    "enabled": true                            // 用户在 UI 勾选后才参与识别
}
```

`enabled: false` ≠ 死代码,**不要删**。它表达"等用户开了开关再启用"。判断是否真死的标准:

- ❌ `enabled: false` + 无任何 `interface.json` / `context.get_node_data()` 引用 → 真死代码
- ✅ `enabled: false` + `interface.json` 有对应 option → 运行时开关,**保留**
- ✅ `enabled: true` 但暂时无 `next` 引用 → 预留节点(见 §9.3)

### 9.8 ❌ 同一文件内重复 ROI
```jsonc
"BigMap_Activity_Resident": { "roi": [21, 46, 685, 133], ... },
"BigMap_Activity_TimeLimit": { "roi": [21, 46, 685, 133], ... },
"BigMap_Activity_GiftPackage": { "roi": [21, 46, 685, 133], ... }
```
10 个城堡建筑 / 3 个 activity tab 都有同样问题。**没有银弹**(Pipeline 协议不支持 ROI 共享),但应该**用 OCR `expected` 的差异让各节点独立**。

### 9.9 ❌ 模板匹配 ROI 太宽
`return.png` 是固定图标,`roi` 应该窄(如 `[603, 0, 117, 140]`);但**全屏搜**会让 200ms 变成 1s+。

### 9.10 ❌ 在单条 `next` 里同时给真转移和 `[JumpBack]`

```jsonc
{
    "CastleMarrySelectStart": {
        "next": [
            "CastleMarrySelectCountry",   // 真转移
            "CastleMarrySelectReject",    // 真转移
            "[JumpBack]CastleMarrySelectCountrySweepDown"  // 子例程
        ]
    }
}
```
这是**正确**用法（多个分支），但要确保**每个非 JumpBack 项都不会重入**——否则会变成循环。
